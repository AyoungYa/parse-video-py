## 微博视频下载（demo）

- 需求：下载 `https://weibo.com/u/1653382134?tabtype=newVideo&layerid=5352520387920686` 到 demo/。
- **坑**：`layerid` 是**微博正文 post id**，不是 h5 视频 oid。
  - `h5.video.weibo.com/api/component` 传 post id → 返回 `Component_Play_Playinfo: null`。
  - `m.weibo.cn/statuses/show?id=<postid>` 被跳 Sina Visitor System（无 Cookie）；但 `m.weibo.cn/api/statuses/show?id=<postid>`（带 iOS UA + `X-Requested-With: XMLHttpRequest`）**可返回 JSON**。
- **正确解析路径**：post JSON → `url_objects[].object.object.target_url` → `https://video.weibo.com/show?fid=1034:5352485540528149` → 用项目 `parse_video_share_url()` 得到无水印直链（默认取 urls 第一条 = 最高码率，本例 mp4_2160p）。
- 下载注意：4K 源约 1.03GB / 19.4min，httpx 流式下载会超时被杀；**改用 curl -C - 后台跑**（约 7MB/s，2.5 分钟下完）。
- 防盗链请求头：`Referer: https://weibo.com/` + 桌面 Chrome UA（与 `utils.build_download_header_candidates` 一致）。
- 产物：`demo/weibo_1653382134_王啸坤.mp4`（3840x2160, h264, 30fps, 1164.78s, 1079166714 B），ffprobe 校验通过。

## 微博 4K 视频去水印（video-watermark-removal skill）

对象：`demo/weibo_1653382134_王啸坤.mp4`（4K 3840x2160，19分24秒，34941 帧，舞台灯光场景）。

### 水印定位（4K 坐标，右上角）
- 形态与 1080P 一致：平台 logo + 第一行标题 + 第二行 `@作者 关注`。
- 精确边界：logo x2980–3170 y128–252；第一行文字 x3196–3730 y140–248；
  第二行 x3464–3732 y262–326。总 bbox **x2980–3732 y110–326 (752×216)**。
- 工作窗口：`x=2940 y=80 w=840 h=280`，提 mask 成功（`demo/wm_work/mask_4k.png`，探索通过无遗漏）。
- 给 verify 用的带留白版：`--x 2910 --y 50 --mask mask_4k_pad.png`（900×340）。
- 定位关键：**时域 min 投影（lo>150）** 才是白字判据，4K 舞台片 std 基线高达 67，
  用默认 `card-std=30` 会把动态背景误判成卡片（触边假告警）。

### ★ 性能：MPS 加速是 4K 场景的命门
- `lama_apply.py` 原版硬编码 `device="cpu"` → 4K ROI 872×312 要 **10s/帧**（全片 88 小时，不可行）。
- **已给 skill 加 `--device auto|cpu|mps|cuda`**（auto 优先 cuda>mps>cpu）+ `_sync_accel()`
  （MPS/CUDA 异步，计时与贴回前需 synchronize）。
- 实测提效：ROI 872×312 CPU 6.9s → MPS **1.05s**（6.5×）；560×224 CPU 2.4s → MPS 0.27s（8.9×）。
- 端到端 MPS 流式 **~1.2s/帧**。全片 34941 帧 ≈ **11.6 小时**，拆 2 路 ≈ 5.8 小时。
- LaMa 耗时随 ROI 面积超线性增长（`pad_out_to_modulo=8` 不缩放，原尺寸进模型）。

### 打样结果（8 秒 / 240 帧，start=300）
- `demo/wm_work/t4.mp4`，290 秒渲完。ASCII 对比：原片水印区有明显笔画，成片变成
  平滑舞台纹理，**文字全部消失且是真实纹理重建**（非涂抹块）。视觉验收通过。

### ★ verify.py 在 4K 短片段下会"尺子坏掉"
- `excerpt_offset()` 的探测 ROI **硬编码 1080P 坐标** `(1444,14,452,196)`，4K 片匹配失效
  → 自动估出"原片起点 0.00s"（实际是 300s）→ ① ② ③ 全部"抽样失败 n=0"，但结论误报 ✅。
- 规避：全片验收时 `dur_clean ≈ dur_src`，走非短片段分支，不依赖 excerpt_offset。
  短片段验收需给 verify 传正确的 `--x/--y` 且**改掉那个默认 ROI**（skill 待修）。

### ★ 新增 `--start-hint`（坑 31）：4K 长片打样验收的救命参数
- **现象**：`verify.py` 对 4K 长片打样做短片段定位时，进程活着但 %CPU ~2%、日志零输出、挂 29 分钟。
- **根因**：粗搜扫**整个原片**。n_scan=(1164.7-8)×30≈34703 帧；每次 `score()`=3 次 `gray_at(src)`;
  4K `-ss` seek 解一帧 ~2s → 粗搜 1~2 小时（低 %CPU 是卡在等 ffmpeg）。
- **修复**：加 `--start-hint <秒>`（= lama_apply 的 `--start`），命中就跳过全片粗搜，
  只在 hint±2s 做帧级精修。
- **实测**：`--start-hint 300` → 起点估出 **299.97s**，总耗时从 1~2 小时压到 **<2 分钟**。
- **另发现（坑 32）**：Python stdout 重定向到文件是**块缓冲**，长任务日志会长时间 0 字节；
  启动必须 **`python -u`** 才实时。别把"日志没输出"当成"进程挂了"。
