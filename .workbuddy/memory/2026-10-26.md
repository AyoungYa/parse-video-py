### 根因（数值定位，模型不能读图就靠量）

1. **`lama_apply.py` 第 94 行是整块 ROI 回贴**：
   `result[y0:y1, x0:x1] = cv2.cvtColor(out_arr,...)` —— ROI = bbox + `pad*3`（默认 30px）
   外扩整块 448×190，**LaMa 输出的整个 ROI 覆盖回帧**，只有 mask 内需要修复，
   **mask 外的真实像素在 30px 圈内全被换成 LaMa 重建值**。全卡片 mask 时恰好全覆盖看不出，
   稀疏 mask 下这一圈真实细节被抹掉。
2. **全卡片 mask 把"真实背景"也重绘了**：水印卡片内部有 32,177px 是**透出来的真实画面**

3. `build_mask.py --grow 21`（默认）会把白字周围约 10px 再吃掉一圈，`--grow 7 --close 5`
   更精细（覆盖率 26%→18.8%），笔画模板覆盖率仍 **100%（漏 0px）**。

### ★★★★ v3 返修（用户第三次反馈"水印没完全去除"）：mask 漏了半透明柔边层

**这是本轮最严重的疏漏，根因是"我的验证判据正好绕开了漏掉的那部分"。**

- `build_mask.py --white-th 168`（默认）只抓「够白」的像素（min 投影 >168）。
  本片水印不止白字，还有**一层半透明柔边/雾面底**（时域 min 投影 100~180）。
  这些像素被当成背景 → **mask 外漏 571 px，mask 内另有 1657 px 没修透**。
- **成片上这些漏网像素比邻域亮 +63 ~ +100（逐点最高 +131）→ 肉眼可见白色残影。**
- **★ 为什么我前两轮没发现**：我一直用「白字模板（min>180）」验残留，
  **模板里根本不含半透明层**，所以永远报"干净"。**验证判据的覆盖范围必须 ≥ mask 漏掉的区域。**
  → **自检口诀：换一个比建 mask 时更低的阈值再验一遍**（建 mask 用 min>100，
  验残留也要覆盖 min>100~180 这段）。

**正解：直接用半透明判据重建 mask**
```python
F  = 全片逐帧灰度（1fps × 146 帧）
mn = F.min(axis=0)                    # 时域最小投影：水印恒亮，全片最暗时也亮
m  = (mn > 100)                       # ★ 100 而非 168 —— 抓住柔边/半透明层
m  = cv2.morphologyEx(m, MORPH_CLOSE, 5x5)
m  = cv2.dilate(m, 3x3, 1)            # 盖抗锯齿边
# 去掉 <20px 的噪点连通块
```
结果 `mask_soft.png` = 15653 px（31%），距 bbox 边 9~11px 无触边。

**打样验证（t=20s）**：漏掉的 571 px 上「成片-邻域差」**+100.11 → +0.19**（逐点 +0.2/+0.3/−0.0）。
质量：细节比 0.87、帧间差比 0.99、mask 内梯度 p90 20 vs 周边 26（正常）。

| mask | 像素 | 半透明层残留 | 说明 |
|---|---|---|---|
| mask.png（white-th 168, grow21） | 13095 | +100 | ❌ 漏柔边 |
| mask_fine.png（grow7） | 9470 | +100 | ❌ 更漏（只为解决"模糊"收窄） |
| **mask_soft.png（min>100）** | **15653** | **+0.19** | ✅ |

**教训链**：
1. v1 用全卡片 → 真实像素被重绘 → **模糊**（用户反馈1）
2. v2 收精细 mask → 模糊解决但**漏柔边** → **残留**（用户反馈2）
3. v3 用 min>100 建 mask → 两者兼得
→ **"不过度重绘"和"不漏修"是一对矛盾，正解是用像素证据精确定义水印边界（min>100 含柔边），
而不是靠 grow 参数拍脑袋。**

### 通用教训（要写进 skill）

- **★ 稀疏 mask 的前提是"只回贴 mask 内"**。skill 的 `lama_apply.py` 整块回贴，
  用稀疏 mask 等于把 mask 外一圈真实画面也换成重建值 —— 这是"看起来还行但局部发糊"的常见来源。
  **建议：把 maskonly 合成做成 lama_apply 的默认（或 `--blend-mask-only` 开关）。**
- **判断"模糊"要看真实像素保持率 + 梯度分布**，不是看残留、也不是看 σ 比。
  `hole = bbox内 & ~dilate(mask,5)` 的高频 std 成片/原片之比：全卡片只有 33~39%。
- 模板覆盖率自检：`mask[tpl].mean()` 必须 100%，收精细 mask 后务必复查（本轮 grow7 仍 100%）。
- **verify ① 在稀疏 mask 下会偏高**（本轮 +4.6 > 3）：mask 窄 → 基线升到 +81.1，
  ROI 内全局时域平均把 mask 外真实画面的帧间变化也算进去。**以局部口径（笔画位-邻域中值）为准。**

## weibo-261021.mp4 二次返修：用户反馈"仍有痕迹" → rowfill 行插值根治

**背景**：10-21 交付的 LaMa 全卡片成片（`weibo-261021_clean.mp4`）verify 全绿，
但用户 10-26 反馈**仍有去水印痕迹**（附截图，模型不能读图，改用数值诊断）。

### ★ 痕痕根因（数值诊断定位）：LaMa 在纯平背景上「发明伪纹理」

这片背景是**平滑渐变亮面**（周边环 detail-σ 仅 0.12~0.18，水平剖面单调下降）。
诊断三件套 + 残留判据全绿，但两项隐藏指标超标：

| 指标 | LaMa 修复区 | 周边参照 | 病因 |
|---|---|---|---|
| 高频纹理能量（Laplacian） | **0.856** | 0.21~0.45 | LaMa 在纯平区发明周边不存在的伪噪点（粗糙补丁感） |
| 帧间差（闪烁） | **0.254** | 0.08~0.19 | 逐帧独立推理 → 伪纹理逐帧随机 → 播放沙沙闪 |

LaMa 在高纹理数据上训练，面对纯平输入倾向"脑补"纹理，且逐帧脑补不同。
**不是参数问题，是模型本性。** 时域中值也压不掉（中值底板 Laplacian 0.707 ≈ 单帧 0.856，
伪纹理大部分时间稳定）。

### ★★ 正解：行插值填充（rowfill.py）—— 渐变背景的理论最优解

背景是平滑渐变时，水印区内容**根本不需要"发明"**——左右锚点线性插值就是答案：

```python
la = frame[:, AL0:AL1].mean(axis=1)   # 每行左锚点带均值（卡片外 6~30px）
ra = frame[:, AR0:AR1].mean(axis=1)   # 每行右锚点带均值
interp = la[:,None,:]*(1-t) + ra[:,None,:]*t   # 逐行线性过渡
# + 高斯羽化边界 + 按环 detail-σ 补微噪（σ≈0.12，防塑料感）
```

**实测对比（同片，rowfill 直接从原片生成，跳过 LaMa）**：

| 指标 | LaMa 全卡片 | **rowfill** |
|---|---|---|
| 高频纹理能量 | 0.856 | **0.513**（落在周边 0.23~0.49 内） |
| 帧间闪烁 | 0.254 | **0.111**（与周边持平） |
| 水印残留（相对口径） | +1.5 | +1.7（同级，均无残留） |
| 亮度差（区内−环） | −1.6 | **−0.4** |
| verify 三件套 | 全绿 | 全绿（① −0.0 / ② 一致 / ③ 0.62） |

**弯路（都试过）**：
- 低通抹平+补噪（flatten_fix.py，blur σ=4/6）：纹理只降到 0.715/0.601，闪烁不降
  （补的新噪自己也在闪）。不如 rowfill 干脆。
- 时域中值底板：压不掉时间稳定伪纹理，且场景非纯静态（首末帧差 5.4）会拖影。

## Chrome cookie 提取原理调研（桌面应用读浏览器登录态）

本机实测环境：Chrome **155.0.8059.86**，cookie DB `Default/Cookies`（注意不是 `Default/Network/Cookies`），
`meta.version = 24`，1336 条全部 `v10` 前缀、无明文行；`Local State` 的 `os_crypt` 为空
（macOS 不吃 Windows 那套 app-bound key）。**结论：macOS 上仍是 Keychain + AES-128-CBC，未上 v20。**

- 算法链：`security find-generic-password -s "Chrome Safe Storage" -w` → PBKDF2-HMAC-SHA1
  (salt=`saltysalt`, 1003 iter, 16B) → AES-128-CBC(IV=16 空格) 解 `encrypted_value[3:]` → 去 PKCS7 →
  **schema ≥24 且明文前 32 字节 == SHA256(host_key) 则剥掉**（Chrome 130+ 加的域绑定前缀）。
- 三个必踩坑：
  1. `sqlite3` 默认 `text_factory` 会把 BLOB 当 UTF-8 解码 → 报
     `Could not decode to UTF-8 column 'encrypted_value'`，必须 `con.text_factory = bytes`。
  2. DB 被 Chrome 独占 → 必须先把 `Cookies` + `-wal` + `-shm` 拷到临时目录再读（否则读到旧数据/锁死）。
  3. **Chrome 136+ 忽略 `--remote-debugging-port`**（除非配非默认 `--user-data-dir`），
     所以"启动带调试端口的 Chrome 读 cookie"这条路对日常 profile 已失效。
- 合法替代：`chrome.cookies` 浏览器扩展（用户自己装）、CDP `Storage.getCookies`、
  Playwright `storageState`、Chrome DevTools MCP `--autoConnect`（用户显式同意）。
- 验证脚本（一次性）：`/tmp/cookietest/demo.py`，实跑 bilibili 域名 4 条全部正确解密。
