### 关键技术点（都踩过）

1. **`-ss` 必须在 `-i` 之前**才是关键帧跳转。放之后要先解码再丢弃前置帧，
   4K 7239 帧取第 7000 帧实测 30 秒。前置后 0.3s。
2. **`SimpleLama` 前两次推理慢**（1234ms → 572ms → 稳定 300ms），是 MPS 内核
   首次编译 + 显存池扩张。加 `warmup()` 预热，用户第一次点就是真实耗时。
3. **任务成败必须看退出码**，不能看日志里有没有「完成」——`echo 'ALL DONE'`
   是 shell 回显，中间命令全崩也照打（实测：lama_apply 抛 ValueError，
   任务被报成 done，成片根本不存在）。现用 `set -o pipefail` + 每阶段 `$?`
   + 结尾 `=== EXIT rc=N ===` + **rc=0 时还要确认成片存在**。
4. **子进程 cwd 必须配绝对路径**。把 cwd 设成工作区目录后，相对路径
   `demo/x.mp4` 在那里解不开 → ffprobe 返回空 → `probe_size` 解包崩。
5. **`build_mask.py` 的 sample_stack 每帧启一个 ffmpeg**，200 帧 40s。
   本地改为单次解码批量抽帧 → 2.8s，与脚本 mask 的 **IoU 0.957**、bbox 完全一致。
6. **`FileResponse` 不支持 Range**，浏览器 `<video>` 拖不动进度条。手写 206 响应。
7. `card_mask_from_sparse` 拆到 `mask_ops.py`（原来在 engine.py，顶层 import PIL
   导致纯 cv2 测试也拉 torch）。

### ★★ 建 mask 的内存炸弹（已修，务必先读）

**症状**：短片段（8s 1080P）建 mask 峰值就 **2.3GB**；长片按模型推算要 **29~77GB**。

**根因**：`video.grab_frames_many` 一律**整区间解码**——
`select='between(n,lo,hi)'` + `capture_output=True` 会把 `[lo,hi]` **所有帧**的 rawvideo
一次性读进内存再挑帧。要的只有 120 帧，却买了整个区间的账。

| 片 | 区间 | 单帧 | 峰值 | 需要 | 浪费 |
|---|---|---|---|---|---|
| 8s 1080P | 166帧 | 5.9MB | 1.7GB | 738MB | 2x |
| 152s 1440P | 3739帧 | 7.9MB | **29GB** 💥 | 984MB | 31x |
| 290s 1440P | 7177帧 | 10.5MB | **77GB** 💥 | 1.3GB | 59x |

**修法（两处）**：
1. `video.py` 加 `_grab_at_ts()`（输入级 seek 单帧）+ `BATCH_DECODE_LIMIT = 1 GiB`；
   `grab_frames_many(path, indices, max_bytes=None)` 按「跨度×单帧 > 上限」分流到逐帧 seek。
   **逐帧 seek 内存恒定 = 单帧**，与片长无关。
2. `masks.py`：`_MAX_MASK_FRAMES = 60`（原 120），调用时传 `max_bytes=n*单帧*2`。

**实测**：152s 1440P **30GB→637MB**；290s **77GB→782MB**；8s 1080P **2.3GB→506MB**。
**精度无损**：同 bbox 下新旧 mask **IoU = 1.0000、逐像素 100% 相同**（抽帧 60 vs 120 结果一致）。

**顺带记住**：`subprocess.run(capture_output=True)` 处理视频 rawvideo 时
**内存 = 输出字节数**，不是缓冲区大小。任何「整区间解码」都要先算 `帧数 × 单帧字节`。
回归测试：`TestBatchDecodeMemoryGuard`（3 例）。

**本机环境坑（再记一次）**：`ps` 命令在本机被系统权限拦（`Operation not permitted`）；
测当前 RSS 要用 ctypes 调 `task_info(mach_task_self(), MACH_TASK_BASIC_INFO)`。

## ★ MPS / CPU / AUTO 三档设备（实测 + 发现一个真 bug）

**AUTO 的挑选顺序**（`engine.py` `resolve_device()`）：cuda → mps → cpu。
本机 Apple M1（arm64）、torch 2.14.1、`cuda.is_available()=False`、`mps.is_available()=True`
→ **AUTO 实际等于 MPS**。

**实测 1080P 微博区（bbox 1484,44,392,136 / pad10 / 矩形 mask）单帧修复**：
| 设备 | 加载 | 首帧 | 稳定 |
|---|---|---|---|
| MPS | 1.7s | 1.67s | **0.296 s/帧** |
| CPU | 1.0s | 1.72s | **0.843 s/帧**（慢 2.8×） |
4428 帧全片：MPS ≈ 22 分钟，CPU ≈ 62 分钟。

**★★ 发现的真 bug（尚未修，等用户确认）**：
`LamaEngine.get()` 是单例，`__init__` 只在**第一次**创建时读 device，之后 `get('mps')`
直接返回旧实例、`_device_pref` 不变 —— 页面上切设备**完全不生效**。
```
先取 cpu -> cpu | pref=cpu
再取 mps -> cpu | pref=cpu     ← 改了没用
同一个实例? True
```
后果：先预览过（cpu 或 auto）、再改成 MPS，仍按旧设备跑，用户会莫名觉得"怎么还这么慢"。
修法：`get()` 里比较传入 device 与实例 `_device_pref`，不一致就丢旧实例重建（代价 1~2s 重载模型）。
