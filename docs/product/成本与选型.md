# 无痕匠 · 云选型与成本模型

> 2026-11-04。本文回答两个问题：**买什么机器**、**每条视频到底花多少钱**、**因此定价该怎么改**。
> 成本模型脚本可复跑：`docs/product/cost_model.py`（参数在文末「待实测校准」里，实测后替换即可）。

## 一、选型结论（先给结论）

| 层 | 选型 | 理由 |
|----|------|------|
| Web / API / 队列 | **阿里云轻量应用服务器 2核4G**（¥379/年） | 200M 峰值带宽、**不限流量**——视频业务的上下行流量是决定项 |
| 对象存储 | **阿里云 OSS 标准存储** + 流量包 | 与服务器同厂商走内网（流出免费）；有**闲时流量半价**（00:00-08:00），契合「夜间跑批、白天交付」 |
| **GPU 渲染** | **本地优先**：Mac（开发期）→ 自建单卡 4090 PC（正式期） | **不租云 GPU**。自建月成本 934 元、日产能 576~720 视频分钟（云 T4 的 4 倍），等效算力 3~5 个月回本。详见 `算力部署方案.md` |
| 数据库 | MySQL 8（与 Web 同机起步） | 冷启动同机自建即可，避免 RDS 每月多 200+；选 MySQL 而非 PostgreSQL 是因为整个方案按 MySQL 落地（本地/线上统一，不做 SQLite 回退） |
| 域名 | wuhenjiang.com（主）+ wuhenjiang.vip（防御） | 建议放腾讯云注册（首年省 ¥20），**备案走阿里云接入** |

> ⚠️ **一条硬约束**：家庭宽带不允许对外提供 Web 服务、也无法备案。所以「Web 也放本地」只能用于开发自测，
> **正式对外的 Web 必须在已备案的云服务器上**，本地只承担 GPU worker 角色。架构见 `算力部署方案.md`。
>
> 云 GPU 只作为**补峰/兜底**保留：日需求超过 400 视频分钟、或 B 端客户要求 SLA 时才启用（触发门槛见 `算力部署方案.md` §6）。

**关于「域名在腾讯云、服务器在阿里云」**：完全可行。ICP 备案跟的是**服务器接入商**，不是域名注册商。所以域名在哪买纯看价格。

### 为什么不是腾讯云

腾讯云轻量单价更便宜（2核4G ¥188/年 vs 阿里云 ¥379/年），但**带宽模型相反**：

| | 阿里云轻量 | 腾讯云轻量 |
|---|---|---|
| 带宽 | 200M **峰值**，不限流量 | 3~12M **固定**，含 500GB/月流量包 |
| 超量 | 不产生账单 | 按量计费，超包单价高 |
| 风险 | 高峰期可能被限速（不保 SLA） | 冲量时流量账单不可预测 |

视频业务的流量是**双向大额**：用户上传 + 成片下载 + 预览对比（前后两份）。500GB/月的包按 100MB/条估算只够 2500 条全流程，一次推广就可能打穿。**成本可预测性 > 单价便宜**，所以选阿里云。

> 一个反直觉点：`2核4G ¥188/年` 和 `¥379/年` 的差价（¥191/年）在总成本里几乎看不见——一台 GPU 一个月就是 ¥900~1700。**别在服务器上纠结几十块，要在 GPU 利用率和处理时长上抠。**

## 二、架构

```
                    ┌────────────────────────────────┐
  用户 ──上传──▶    │  轻量服务器 2核4G（已备案）      │
                    │  Web / API / 任务队列 / 交付页   │
  用户 ◀─下载──    │  （不跑任何推理）                │
                    └───────────┬────────────────────┘
                        ▲       │ ① 任务元数据（不传视频）
       ② worker 主动出站 ─┘      │
          长轮询领任务            │
                    ┌───────────▼────────────────────┐
                    │  豆豆本地 PC（4090 / Mac）       │
                    │  LaMa 渲染 + 验收指标            │
                    └───────────┬────────────────────┘
                       ③ 签名 URL 直传 │ 不经服务器中转
                    ┌───────────▼────────────────────┐
                    │  OSS（临时区，TTL 24h 自动删）    │
                    └────────────────────────────────┘
```

**关键设计**：本地机在 NAT 后面，所以由 **worker 主动向云端领任务**（出站 HTTPS），而不是云端来调它。
视频文件走 OSS 签名 URL 直传，不占云服务器带宽。完整协议与可靠性设计见 `算力部署方案.md`。

**两段式推进**：
- α/β 开发内测期 → 渲染挂在本机 Mac（MPS 现成可用），Web 也可先同机 + Cloudflare Tunnel 自测，**零成本**
- 正式公测期 → Web 上云备案，渲染迁到自建 PC，worker 模式接入

## 三、单条视频成本模型

### 参数（保守取值，待实测替换）

| 参数 | 取值 | 说明 |
|------|------|------|
| LaMa 吞吐（T4） | **12 fps** | 规划值；Mac MPS 实测 1080P ROI 0.21s/帧≈4.8fps，CUDA 按其 2~3 倍估 |
| LaMa 吞吐（A10） | 20 fps | — |
| GPU 小时价（T4） | ¥2.30 | 包月 ¥1681 ÷ 730h |
| 1080P 码率 | 60 MB/分钟 | H.264 ~8Mbps |
| 4K 码率 | 240 MB/分钟 | — |
| 外网流出 | ¥0.5/GB | OSS 标准价（闲时 ¥0.25） |
| 下载倍数 | 1.5× | 预览一份 + 成片一份 + 余量 |
| 4K 帧成本倍数 | 4× | ROI 面积约为 1080P 的 4 倍，LaMa 耗时按面积放大 |

> **关键建模假设**：LaMa 只处理 ROI 裁剪块，所以**成本主要由「帧数 × ROI 面积」决定，与整片分辨率关系不大**。这条假设决定了后面所有降本策略的方向。

### 每分钟视频的变动成本

| 场景 | GPU 成本 | 流量成本 | **合计** |
|------|---------|---------|---------|
| 1080P / T4 / 利用率 30% | 0.319 | 0.044 | **0.363 元** |
| 1080P / T4 / 利用率 50% | 0.192 | 0.044 | **0.236 元** |
| 1080P / T4 / 利用率 70% | 0.137 | 0.044 | **0.181 元** |
| 1080P / A10 / 利用率 50% | 0.223 | 0.044 | 0.266 元 |
| 4K / A10 / 利用率 50% | 0.890 | 0.176 | **1.066 元** |

**规划基准取「1080P / T4 / 50% 利用率 = 0.24 元/分钟」**，即以 0.24 元/分钟做所有决策。

### 单条视频加工成本

| 时长 | 1080P（T4） | 4K（A10） |
|------|------------|-----------|
| 15s（试用档） | **0.06 元** | 0.27 元 |
| 30s（签到档） | **0.12 元** | 0.53 元 |
| 1 min | 0.24 元 | 1.07 元 |
| 5 min | 1.18 元 | 5.33 元 |

## 四、四个必须现在就修的数字

模型跑完，**商业化方案里有三处需要修正**：

### ① 包月「300 分钟/月」上限会亏钱 ❌

按 0.24 元/分钟，¥49 包月的毛利随用量塌陷：

| 月用量 | 成本 | 毛利 | 毛利率 |
|--------|------|------|--------|
| 10 min | 2.65 | 46.35 | 94.6% |
| 20 min（典型用户） | 5.01 | 43.99 | **89.8%** |
| 50 min | 12.07 | 36.93 | 75.4% |
| 100 min | 23.86 | 25.14 | 51.3% |
| 200 min | 47.42 | 1.58 | 3.2% |
| **300 min** | **70.98** | **-21.98** | **-44.9%** |

**修正：公平使用上限从 300 分钟下调到 100 分钟/月**。100 分钟对应毛利率 51%，仍有安全垫；重度用户超出后按 ¥0.6/分钟加购（成本 0.24，毛利 60%）。

好消息是**典型用户（20 分钟）毛利率 90%**——只要拦住那 1% 的滥用用户，这个生意的成本结构非常健康。

### ② 签到「每日 +2 分」是成本黑洞 ❌

原设计 +2 分/天、1 分 = 30s 视频，即**每天白送 1 分钟处理量**：

- 重度签到用户成本 = **7.07 元/月/人**
- 1000 个只签到不付费的用户 = **7,070 元/月** 纯烧钱，比 GPU 包月还贵 4 倍

**修正方案（三选一或组合）**：
- 签到 +1 分/天（成本减半至 3.5 元/月）
- 积分月累计封顶 10 分（最多抵 5 分钟）
- 积分仅可处理 **≤15s** 且需登录 + 手机号验证

建议：**签到 +1 分 + 月累计封顶 10 分**。积分的作用是养成打开习惯，不是送免费额度。

### ③ 4K 不能算包月权益 ❌

4K 单位成本是 1080P 的 **4.5 倍**（1.07 vs 0.24 元/分钟）。30 分钟 4K 一条就是 ¥32，两条就把包月钱吃光。

**修正：4K 独立计费**，包月每月赠 2 条 4K 额度（≤5min），超出按 4 倍积分扣。这样「4K 支持」仍是卖点，但不会被当成无限自助餐。

### ④ ✅ 免费试用的成本低到可以更慷慨

单个试用用户（3 条 × 15s）成本 **0.18 元**。这个数字很低——意味着**真正的风险不是被薅，而是转化不够**。

可以放大试用：**3 条 × 30s（成本 0.36 元/人）**，甚至给到 5 条。按 1000 个试用用户算，总成本 ¥360，只要转化 8 个包月用户（¥392 首月收入）就回本。**试用档应该更大方，这才符合「靠体验卖确定性」的逻辑。**

### 打平所需订阅数（典型用户 20 分钟/月，扣 0.6% 支付手续费）

| 定价 | 单用户月毛利 | 已有 PC 口径（138 元） | 新增设备口径（972 元） | 云 GPU 口径（1718 元） |
|------|------------|---------------------|--------------------|--------------------|
| ¥39 | 34.05 | **5 人** | 29 人 | 50 人 |
| ¥49 | 43.99 | **4 人** | 22 人 | 39 人 |

**结论：PC 已存在把打平门槛压到 4 个订阅**——这意味着上线第一天就可能盈利，冷启动完全没有资金压力，可以专心把全绿率磨到 90%。

> **定价仍建议 ¥49**：打平只需 4 个用户之后，定价的考量完全不再是保本，而是价值锚定与价格带占位。
> ¥49 留出的 100 分钟上限 + 4K 额度更从容，且仍在竞品 ¥30~70 区间内。用「验收报告」做溢价支撑。

## 六、成本优化杠杆（按收益排序）

如果后续成本有压力，按这个顺序动手：

| 优先级 | 手段 | 预期收益 | 代价 |
|--------|------|---------|------|
| **1** | **提 GPU 利用率**（队列攒批、夜间跑批、错峰交付） | 利用率 30%→70% 成本降 **50%** | 交付延迟变长（需产品侧配合，如「夜间优先」档便宜） |
| **2** | **限总时长**（而非限分辨率） | 线性 | 无 |
| **3** | **batch 推理 + fp16** | 吞吐 2~3× | 需改 `engine.py` 的批处理（工作量小） |
| **4** | **收紧 ROI padding**（水印框别开大） | LaMa 耗时按面积超线性，砍 30% 面积约省 40% 时间 | 需定位更精准 |
| **5** | **闲时流量半价**（凌晨出片、白天不重下） | 流量成本 -50% | 影响体验 |
| 6 | 降分辨率 | **几乎不省 GPU**（ROI 绝对尺寸不变），只省流量 | 影响画质，性价比最低 |

> ⚠️ 第 6 条要特别注意：**「免费档降到 720P」这个常见做法对本产品几乎无效**。限时长才是唯一有效的手段。这也解释了为什么现有方案里「免费 15s」的设计是对的。

## 七、待实测校准的三个数（决定模型准不准）

模型里三个数是估的，**必须在上线前用真实数据替换脚本常量**：

1. **LaMa 在目标机型上的真实 fps** —— Mac MPS 有实测（1080P ROI 0.21s/帧 ≈ 4.8fps），**自建 4090 的值必须补测**（脚本现按 T4 12fps × 4 倍关系推算为 48fps）。实测方法：跑一条 1 分钟样片，`time` 一下 `lama_apply` 即可。若只有一半，包月上限要再砍半。
2. **真实 ROI 平均面积**（影响 4K 倍数 4×）——统计 20 条真实用户样片的 mask bbox 面积分布。
3. **真实用户月均用量**（影响毛利率）——上线 4 周后看 P50/P90 分位数，用 P90 校验 100 分钟上限是否合理。

> 这三个数拿到之前，**不要把包月上限写死在产品文案里**，用「初期 100 分钟，后续可能调整」的措辞留出空间。

## 八、一句话总结

**这个生意的成本结构很好（典型用户毛利率 90%），坑不在算法也不在服务器，而在「免费额度」和「公平使用上限」这两个数字——它们现在都设错了，一个是黑洞（签到），一个是亏损线（300 分钟）。改完这两个数字，模型就成立了。**

**算力放本地又把打平线从 39 人压到 4 人**（PC 已存在，只计电费）——冷启动完全没有资金压力，可以专心磨全绿率。代价是可用性和 4K 体验，落地细节见 `算力部署方案.md`。
