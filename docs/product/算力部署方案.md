# 无痕匠 · 算力部署方案（本地优先）

> 2026-11-04。基调：**早期阶段的渲染算力跑在豆豆本地（Mac）或自建 PC 上，不租云 GPU。**
> 本文解决三件事：这样跑**怎么落地**、**有什么硬约束**、**什么时候该搬到云**。
> 成本推导见 `成本与选型.md`；可复跑 TCO 脚本见 `docs/product/local_tco.py`。

## 一、结论先讲

| 阶段 | 形态 | Web 服务 | 渲染算力 | 月成本 |
|------|------|---------|---------|--------|
| **开发 / 自测** | 形态 A：全本地 | 本机 + Cloudflare Tunnel | 同一台 Mac | **0 元** |
| **内测 / 公测** | 形态 B：云 Web + 本地 worker | 阿里云轻量（备案） | 豆豆的 PC / Mac | **37 元**（服务器）+ 电费 |
| **规模化（触发条件见 §6）** | 形态 C：云 Web + 云 GPU | 同上 | 阿里云 gn6i / 自建扩容 | 视规模 |

**⚠️ 一条硬约束必须先说**：**家庭宽带不允许对外提供 Web 服务，也备不了案。**
运营商协议明确禁止家用宽带商用建站，家宽也没有固定公网 IP。所以：

- 开发期的「本机跑全栈」只能用 Tunnel 临时访问，**不能作为正式上线形态**
- **正式对外的 Web 必须放在已备案的云服务器上**，本地只承担 worker 角色

好消息是：这个拆分对代码改动很小（见 §3），而且**省钱效果完全保留**——贵的是 GPU，不是那台 2核4G。

## 二、为什么是「worker 主动领任务」而不是「云调本地」

本地机器在 NAT 后面，云端**无法主动连进来**。两条路：

| 方案 | 做法 | 问题 |
|------|------|------|
| ❌ 内网穿透（frp / 花生壳） | 把本地 worker 的 HTTP 暴露到公网，云端回调 | 要维护隧道进程；断线即失联；把内网端口暴露到公网有安全风险；家宽 IP 变动要同步 |
| ✅ **worker 主动出站拉任务** | worker 只发起**出站** HTTPS 长轮询到云端，领任务 → 干完回报 | 零 NAT 配置、零入站端口、断网自动重连。**GitHub Actions self-hosted runner 就是这套模型** |

选后者。核心逻辑：

```
云端（公网）                          本地 PC（NAT 后）
┌──────────────────┐                ┌─────────────────────┐
│ 任务队列 (DB)     │◀── 1.长轮询领取 ──│ worker daemon       │
│ POST /worker/claim│                │  （开机自启）        │
│                  │── 2.签名 URL ───▶│                     │
│                  │                │  3. 从 OSS 下载原片   │
│                  │◀── 4.心跳进度 ───│  4. LaMa 渲染        │
│                  │◀── 5.完成+指标 ──│  5. 成片传回 OSS      │
└──────────────────┘                └─────────────────────┘
        ▲
        │ 用户上传 / 下载成片
        │
   OSS（临时区，TTL 24h）
```

### ★ 两个关键分工原则（豆豆架构的修正版，2026-11-04 定稿）

豆豆提出的架构（PC 轮询 OSS 拿任务、云端轮询 OSS 发现完成）方向正确——**PC 主动拉、文件走 OSS、云只管交互**全部保留。只修正两处分工：

**原则 1 · 控制面走云 API，数据面走 OSS**（任务队列和状态不在 OSS）

「PC 轮询 OSS 找未处理视频」不可行，五个理由：

| 问题 | 说明 |
|------|------|
| OSS 是存储不是队列 | 没有「未处理」语义，只能 ListObjects 全量列举 + 前缀约定（pending/ → processing/ → done/），列举慢、有延迟，对象一多就是灾难 |
| **竞态无解** | 两台 worker（比如 Mac 和 PC 同时在线）同时看到同一个 pending 文件 → 重复处理。OSS 没有原子的「领取」操作；DB 里一条 `UPDATE ... WHERE status='pending' RETURNING` 天然原子 |
| 状态割裂 | 任务状态、进度、验收指标本来就必须在云 DB（付费扣积分、用户页面进度都要用）。放 OSS 等于维护两套状态机，迟早不一致 |
| 元数据别扭 | 任务参数（bbox、方案选择、指标）塞 OSS 对象 meta 的话，改一次 meta 要 CopyObject 重写整个对象 |
| 凭证安全 | 轮询 OSS 要求 PC 持有**长期 AK/SK**；轮询云 API 只需一个 worker token，文件读写拿的是云端**按对象签发的临时 URL**，泄露面小得多 |

**原则 2 · 上传也直传 OSS，云服务器不中转视频**

用户上传不要走「云服务器接收再转存 OSS」。2核4G 的机器中转 500MB 视频会吃满内存和连接，并发几个就顶不住。改为：前端请求云 API → 云端签发**限定 content-type / 大小 / 15 分钟有效期**的直传 URL → 用户浏览器直传 OSS（ali-oss web SDK 现成，支持分片断点）。

**完整链路**（豆豆方案修正后）：

```
① 用户请求上传 ──▶ 云 API 签发临时 URL ──▶ 用户直传 OSS（原片）
② 云端建任务记录（DB：pending）
③ PC worker 长轮询云 API 领任务（拿到含签名 URL 的任务描述，原子置为 leased）
④ PC 从 OSS 下载原片 → 本地渲染（LaMa + 验收）
⑤ PC 把成片上传 OSS，把验收指标一并带上
⑥ PC POST 云 API「完成 + 指标」 ──▶ 云端更新 DB ──▶ 用户页面显示完成
   （不是云端"发现"完成——处理完的时机 PC 最清楚，主动上报零延迟；
     若靠云端轮询 OSS 找新文件，又要回到 ListObjects 的坑）
⑦ 断链兜底：90 秒租约超时 → 任务打回 pending 重派（见 §4）
```

**为什么素材要过 OSS 而不是 PC 直连云端**：本地 worker 与云端之间只跑「任务元数据」，视频文件走 OSS 签名 URL。好处是上传/下载都能断点续传、能走 CDN、云端不用中转大文件（省服务器带宽）。

## 三、改造映射（对现有代码的增量）

现有 `JobManager.start()` 是本机 `subprocess.Popen`，形态 A 直接能用。形态 B 需要加一层「分发」：

| 现有 | 改造 | 工作量 |
|------|------|--------|
| `Job.status: pending/running/done/failed/stopped` | 增加 `dispatching`（已入队待领）、`leased`（worker 已领） | 小 |
| `Job.pid` + 日志文件轮询（`_refresh`） | 远程模式新增 `worker_id` / `lease_expires` / `attempt`，进度改为读心跳上报 | 中 |
| `JobManager.start()` | 保留（形态 A），新增 `dispatch()` 入库待领 | 小 |
| — | 新增 4 个端点：`/worker/claim`（长轮询 25s）、`/worker/heartbeat`、`/worker/complete`、`/worker/fail` | 中 |
| — | 新增 `worker.py`：daemon 主循环 + 心跳线程 + 本地渲染调用 + 断点重试 | 中 |
| — | 租约回收定时任务（见 §4） | 小 |

**合计 3~4 人日**，可并入 M5，也可与 M1 并行（不阻塞管线自动化）。

## 四、可靠性：三个必须处理的事故场景

本地机器跑生产，最大的风险不是性能，是**它会不受控地消失**。

### ① 断电 / 死机 / 断网 → 任务被永久占用

用**租约（lease）+ 心跳续租**：

- worker 领任务时，任务打上 `lease_expires = now + 90s`
- worker 每 15s 心跳一次，续租到 `now + 90s`
- 云端后台每 30s 扫一次：`lease_expires < now` 且状态为 `leased` → 打回 `pending`，`attempt += 1`
- `attempt >= 3` → 标记失败并告警（不要无限重试烧算力）

这就是分布式任务队列的标准做法，必须做——否则一次断电，那个任务在用户界面上永远是"处理中"。

### ② 处理到一半崩了 → 白白重头再来

`lama_apply.py` 目前不支持断点续渲。两个选择：
- **短期（建议）**：接受重头跑。一场 5 分钟片重跑 3 分钟，成本可接受，不为此增加复杂度
- **长期**：按帧区间分段渲染（`--start/--end`），完成段落盘，崩溃后从最后完成段续。留到规模化阶段再做

### ③ 人不在家，服务就停了

- worker 注册为**开机自启**（macOS `launchd` / Windows 任务计划 / Linux systemd）
- 崩溃自动重启（进程守护 + 最多 5 次/小时，防崩溃循环）
- 云端要能优雅降级：队列积压时前端显示「预计等待 X 分钟」，而不是让用户干等
- **诚实提示**：本地算力意味着可用性不是 99.9%，产品文案别承诺 SLA。B 端客户如果要求 SLA，就必须上云（见 §6）

## 五、带宽：本地 worker 的真实瓶颈

链路是「OSS → 本地下载 → 处理 → 上传回 OSS」，**上行是瓶颈**（家宽下行大、上行小）：

| 上行带宽 | 1080P 1min (60MB) | 1080P 5min (300MB) | 4K 1min (960MB) |
|---------|------------------|-------------------|----------------|
| 30 Mbps | 16 秒 | 80 秒 | 256 秒 |
| 50 Mbps | 10 秒 | 48 秒 | 154 秒 |
| 100 Mbps | 5 秒 | 24 秒 | 77 秒 |

**判读**：以自建 4090（约 48fps）处理 5 分钟 1080P 片为例，渲染 187 秒、上行 48 秒（50Mbps）——上传只占 26%，不是瓶颈。但两个必须注意：

1. **并发回传必须限 1**。3 个成片同时上传会堵死上行，还会影响家里其他设备上网
2. **4K 用户尽量引导到云端处理**，或提示"上传较慢"。4K 1 分钟片在家宽 50Mbps 下要 2.5 分钟，体验很差

> 如果家里能办到 100Mbps 上行（很多地区有 1000M/100M 套餐或上行提速包），体验会明显好一档，值得单独花钱。

## 六、什么时候该搬到云（决策门槛）

**别凭感觉迁，看这三个数**：

| 触发条件 | 说明 | 动作 |
|---------|------|------|
| 日处理量 > **400 视频分钟** 持续 2 周 | 自建 4090 日产能约 576~720 分钟（50% 利用率），400 是留 40% 余量的安全线 | 加第二台自建，或上云补峰 |
| 队列等待 P90 > **30 分钟** 持续 2 周 | 说明产能真不够，不是调度问题 | 同上 |
| 有 **B 端客户要求 SLA**（7×24、按时交付） | 本地单点无法承诺可用性 | 必须上云，或本地双机 + 云兜底 |

**在触发之前，自建是明显更优的选择**：

| 对比 | 自建单卡 4090 | 云 T4 包月 |
|------|-------------|-----------|
| 月成本 | **934 元**（折旧 833 + 电费 101） | 1,681 元 |
| 日产能（视频分钟） | **576~720** | 144 |
| 等效算力月成本 | 934 元 | 6,724~11,767 元（4~7 台 T4） |
| **回本周期** | — | **2.8~5.2 个月** |

按等效算力比，自建 3~5 个月就回本。**前提是你真的要用满它的产能**——如果一个月只处理几十条视频，那机器就是闲置资产。

> ★ **现状更新（2026-11-04）：豆豆的 PC 已存在**，采购成本是沉没成本，不进运营账。
> 实际只需计电费 ≈ 101 元/月 → 公测期固定成本降到 **≈ 139 元/月**（电费 + 服务器 + 存储 + 域名），
> 盈亏平衡压到 **4 个订阅**（¥49）。前提是 PC 体检合格（见 §7）。

## 七、已有 PC 的体检清单（2026-11-04：PC 已存在，无需采购）

能不能当渲染机，就看四项，**GPU 是决定性的**：

| 件 | 合格线 | 理想 | 判定 |
|----|--------|------|------|
| **GPU** | **NVIDIA 卡，显存 ≥ 6GB** | RTX 3060 12G / 4070 / 4090（24G） | LaMa 推理吃 4~6GB；显存决定 batch 和最大 ROI。**AMD / Intel 核显不合格**（CUDA 不可用，CPU 渲染慢 10~50 倍） |
| 内存 | ≥ 16GB | 32GB+ | 有 `BATCH_DECODE_LIMIT=1GiB` 分流守卫，16G 能跑，32G 更从容 |
| 系统 | Windows 10/11 或 Linux | Linux 原生 / Windows + WSL2 | 现有管线是 ffmpeg 子进程为主，Windows 可用但要做路径适配（`paths.py` 全部走 `Path` 即可）；**WSL2 的 CUDA 支持很成熟，推荐** |
| 网络 | 有线连接 | 千兆有线 + 上行 ≥ 50Mbps | WiFi 传大文件不稳，会拖慢 OSS 回传（见 §5） |

**检测方法**：在 PC 上开终端跑一行

```
nvidia-smi
```

- 有输出 → 看两处：显卡型号（Name）+ 显存总量（Memory-Total）。把输出发给助手即可判定
- 报"命令不存在"或"不是内部或外部命令" → 要么没 N 卡，要么没装驱动；先在设备管理器确认显卡型号

**体检结果的三条路**：

| 结果 | 方案 |
|------|------|
| N 卡 ≥ 6GB | ✅ PC 直接上位当渲染机，装 CUDA + PyTorch 后跑一条样片标定 fps，成本模型常量落地 |
| N 卡但显存偏小（4GB） | ⚠️ 能跑但 ROI/batch 受限，4K 大水印可能 OOM——1080P 为主可用，4K 留给以后 |
| 无 N 卡 / A 卡 | ❌ PC 不适合跑 LaMa。渲染继续用 Mac（MPS），PC 转「上传中转 + 备用 Web/DB」角色，或当纯开发机 |

> **没体检之前别急着在 PC 上装环境**。如果结果是最后一种，装 CUDA + torch 的两三个小时就白费了。

**位置安排**：放在有网线（不是 WiFi）的房间。满载时注意散热和噪音。

## 八、一句话总结

**「云 Web + 本地 worker」这个组合是对的，成本只有云方案的三分之一，但代价是可用性和 4K 体验。**落地时最要紧的三件事：worker 主动出站（不搞内网穿透）、任务租约（防断电占死任务）、上行带宽限流（防堵家里的网）。

PC 已存在 → **第一件事是体检（`nvidia-smi`），不是装环境**。GPU 型号决定它是渲染主力还是只当备用机，这个判断做完，后面的架构和成本就全部落地了。
